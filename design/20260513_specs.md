# HT Dungeon — Game Specification v0.1

## 1. Game Summary

**HT Dungeon** is a real-time-with-pause dungeon game where one hero explores a procedurally generated dungeon, fights rats, collects rat tails, and manages a small inventory.

The first playable version focuses on:

* One hero
* One dungeon floor
* 10 generated rooms
* Corridors connecting all rooms
* Rats as the only enemy
* Rat tails as the only loot item
* Tile-based dungeon geometry
* Continuous/arbitrary-position movement for actors
* Rust + `wgpu`
* Separate logic and rendering/UI crates running on separate threads

# 4. Threading Model

The game uses two main threads.

## Render/UI Thread

This is the main thread.

Responsibilities:

* Owns `winit` event loop
* Owns `wgpu` device, queue, surfaces, pipelines, buffers
* Receives latest render snapshot from logic thread
* Draws the world
* Draws UI
* Converts mouse clicks to world coordinates
* Sends player commands to the logic thread

## Logic Thread

Responsibilities:

* Owns mutable `GameWorld`
* Runs fixed-step simulation
* Processes commands
* Updates entities
* Runs AI
* Resolves movement, collision, combat, loot pickup
* Produces snapshots for the renderer

## Communication

Use channels.

```rust
Render/UI Thread  --->  Logic Thread
        PlayerCommand

Logic Thread      --->  Render/UI Thread
        RenderSnapshot
```

Recommended crate:

```text
crossbeam-channel = "0.5"
```

Use `crossbeam-channel` for the first version.

Reasons:

* The game uses ordinary synchronous threads, not an async runtime.
* `crossbeam-channel` is mature and well suited for fixed-step worker threads.
* It supports bounded channels, non-blocking receive loops, `select!`, and timer channels.

Recommended channel setup:

```rust
let (command_tx, command_rx) =
    crossbeam_channel::bounded::<PlayerCommand>(256);

let (snapshot_tx, snapshot_rx) =
    crossbeam_channel::bounded::<RenderSnapshot>(2);
```

The command channel should be bounded but large enough for normal UI input bursts.

The snapshot channel should be small because the renderer only needs the newest
snapshot. If the logic thread produces snapshots faster than rendering consumes
them, older snapshots may be dropped.

`flume` is also a good Rust channel crate, especially if async integration is
needed later, but async is not part of this MVP threading model.

# 5. Simulation Timing

The logic thread should run at a fixed tick rate.

Recommended first version:

```text
Logic tick rate: 60 ticks per second
Tick duration: 1 / 60 seconds
```

Rendering may run at the monitor refresh rate.

If rendering is faster than logic:

```text
Renderer reuses the latest snapshot.
```

If logic produces snapshots faster than render can consume:

```text
Renderer keeps only the newest snapshot and drops older ones.
```

If logic becomes slow:

```text
Renderer continues drawing the last known snapshot.
UI remains responsive.
Input commands are queued.
```

# 6. Pause System

The game is **real-time with pause**.

## Running State

When running:

* Hero moves
* Rats move
* Rats detect the hero
* Combat happens
* Cooldowns advance
* Loot can be picked up

## Paused State

When paused:

* Simulation time stops
* Hero does not move
* Rats do not move
* Combat does not progress
* AI does not update
* Attack cooldowns do not advance

But the player can still:

* Move the camera
* Inspect things with right click
* Open inventory
* Select commands
* Click an enemy to queue an attack order
* Click a floor tile to queue a movement order

Queued orders execute once the game is resumed.

# 8. Tile Map

The dungeon is built from roguelike-style tiles.

```rust
enum TileKind {
    Wall,
    Floor,
}
```

Each tile should be mutable because walls and floors may later be destroyed or built.

```rust
struct Tile {
    kind: TileKind,
    hp: Option<i32>,
    revision: u32,
}
```

Recommended first values:

```text

Wall: 10 hp
```

For the first version, walls do not need to be destructible yet, but the data model should already allow it.

# 9. Mutable Dungeon Rendering Choice

Use a **mutable tilemap with chunked GPU updates**.

Do **not** bake the whole dungeon into one static mesh.

Do **not** pre-render the dungeon into one fixed background image.

Instead:

```text
Logic world:
    Mutable tile grid

Renderer:
    Chunked tile renderer
    Each chunk has its own GPU instance buffer or vertex buffer
    Dirty chunks are rebuilt when tiles change
```

Recommended chunk size:

```text
16 x 16 tiles
```

When a wall becomes floor, or floor becomes wall:

1. Logic updates the tile.
2. Logic increments the tile/chunk revision.
3. Logic marks that chunk as dirty.
4. Snapshot tells renderer which chunks changed.
5. Renderer rebuilds only those chunks.

This supports later features like:

* Digging walls
* Destroying floors
* Building walls
* Placing doors
* Collapsing rooms
* Dynamic terrain changes

# 10. Dungeon Generation

## Random Number Generation

Recommended crates:

```text
rand = "0.8"
rand_chacha = "0.3"
```

Use `rand_chacha::ChaCha8Rng` with an explicit `u64` seed.

Seed behavior:

```text
New game with supplied seed:
    Use the supplied seed.

New game without supplied seed:
    Generate a random u64 seed from OS randomness.

GameWorld:
    Store the seed as rng_seed.

Tests:
    Use fixed seeds.
```

Example:

```rust
use rand::SeedableRng;
use rand_chacha::ChaCha8Rng;

let mut rng = ChaCha8Rng::seed_from_u64(seed);
```

All procedural choices for the floor should use this seeded RNG:

* Room sizes
* Room placement
* Corridor orientation
* Rat counts for rooms 3-10
* Rat placement
* Dagger damage rolls

This makes dungeon generation and combat reproducible for tests and bug reports.
The debug UI or startup log should show the active seed.

## First Version Goal

Generate one dungeon floor with:

```text
10 rooms
Different room sizes
Corridors connecting all rooms
Walls around floor areas
```

## Map Size

Recommended first version:

```text
80 x 60 tiles
```

This can become configurable later.

## Room Count

```text
room_count = 10
```

## Room Size

Recommended random range:

```text
Minimum room width:  5 tiles
Maximum room width:  12 tiles

Minimum room height: 5 tiles
Maximum room height: 10 tiles
```

Rooms must have different random sizes.

## Room Placement

Algorithm:

1. Start with a full wall map.
2. Try placing rectangular rooms randomly.
3. Reject a room if it overlaps an existing room.
4. Require at least 1 tile of padding between rooms.
5. Continue until 10 rooms are placed.

Room structure:

```rust
struct Room {
    id: RoomId,
    x: i32,
    y: i32,
    width: i32,
    height: i32,
}
```

## Room Carving

For every accepted room:

```text
Set all tiles inside room rectangle to Floor.
```

## Corridor Generation

Connect rooms with corridors.

Simple first version:

```text
Sort rooms by placement order.
Connect room 1 to room 2.
Connect room 2 to room 3.
...
Connect room 9 to room 10.
```

For each connection:

1. Take center of room A.
2. Take center of room B.
3. Carve an L-shaped corridor.
4. Randomly choose horizontal-first or vertical-first.

Corridor width:

```text
1 tile for first version
```

Later this can become:

```text
1-3 tiles random width
```

## Connectivity Requirement

After generation, verify that all rooms are reachable from the first room.

If not reachable:

```text
Regenerate the dungeon.
```

# 18. Movement

Actors use continuous movement.

They are not locked to tile centers.

## Actor Shape

Use circular collision for hero and rats.

Recommended values:

```text
Hero radius: 0.30 tiles
Rat radius:  0.25 tiles
```

## Movement Speeds

Recommended first values:

```text
Hero speed: 3.0 tiles per second
Rat speed:  2.0 tiles per second
```

## Collision

Actors collide with:

* Walls
* Map bounds

Actors do not collide with:

* Floor
* Rat tail items

Hero and rats use **soft collision** with other actors.

Actors should not treat another actor's center as the movement goal during combat. A unit moving to attack should move only until it is close enough to attack.

Recommended stop distance:

```text
stop_distance = attacker.radius + target.radius + attacker.attack_range
```

If the distance to the target is greater than `stop_distance`, the actor moves toward the target. If the distance is less than or equal to `stop_distance`, the actor stops and attacks.

```rust
let to_target = target.position - attacker.position;
let distance = to_target.length();
let stop_distance = attacker.radius + target.radius + attacker.attack_range;

if distance > stop_distance {
    attacker moves toward target
} else {
    attacker stops and attacks
}
```

The movement goal is not:

```text
target.position
```

The movement goal is:

```text
close enough to target.position to attack
```

## Actor Separation

After movement, resolve actor overlaps with a separation force.

Each actor has a collision circle. If two actor circles overlap, push them apart by the overlap amount.

```rust
let delta = a.position - b.position;
let distance = delta.length();
let min_distance = a.radius + b.radius;

if distance > 0.0 && distance < min_distance {
    let overlap = min_distance - distance;
    let normal = delta / distance;

    a.position += normal * overlap * 0.5;
    b.position -= normal * overlap * 0.5;
}
```

In the movement system, combine desired movement and separation:

```text
final velocity =
    movement toward current goal
  + separation from nearby actors
```

This means an actor can still move toward an enemy, but it should avoid standing inside allies or enemies.

## Attack Range Hysteresis

Use hysteresis for movement-to-attack transitions so units do not jitter at the exact attack boundary.

Use two distances:

```text
attack_enter_range = attacker.radius + target.radius + attacker.attack_range
attack_exit_range  = attack_enter_range + 0.20
```

The actor starts attacking when distance is less than or equal to `attack_enter_range`.

The actor starts moving again only when distance is greater than `attack_exit_range`.

```rust
match actor.state {
    State::MovingToAttack => {
        if distance <= attack_enter_range {
            actor.state = State::Attacking;
            actor.velocity = Vec2::ZERO;
        }
    }

    State::Attacking => {
        actor.velocity = Vec2::ZERO;

        if distance > attack_exit_range {
            actor.state = State::MovingToAttack;
        }
    }
}
```

This prevents repeated switching like:

```text
distance 1.01 -> move
distance 0.99 -> stop
distance 1.01 -> move
distance 0.99 -> stop
```

For the first version with one hero and rats:

1. Hero has a circle radius.
2. Rat has a circle radius.
3. Hero moves toward a rat only until attack range.
4. Hero stops when close enough.
5. Rat also stops when close enough.
6. If actor circles overlap, push them apart.
7. Use attack range hysteresis so actors do not flicker between moving and attacking.

## Diagonal Movement Rule

Diagonal movement is allowed only if the actor fits through the diagonal path.

This means the actor may not cut through wall corners.

For grid pathfinding, moving diagonally from tile `(x, y)` to `(x + 1, y + 1)` is allowed only if:

```text
tile(x + 1, y) is passable
and
tile(x, y + 1) is passable
and
the actor radius has enough clearance
```

For continuous movement, also use swept-circle collision against nearby wall tiles.

This prevents the hero or rat from sliding through a diagonal gap that is visually too small.

# 19. Pathfinding

Use pathfinding over the tile grid, but move actors continuously along the resulting path.

## First Version

Use A*.

Nodes:

```text
walkable floor tiles
```

Edges:

```text
4-directional movement
8-directional movement when diagonal clearance is valid
```

Costs:

```text
Orthogonal move: 1.0
Diagonal move: 1.414
```

Heuristic:

```text
Octile distance
```

## Path Result

A path is a list of waypoints.

The actor follows waypoints using continuous movement.

Later improvement:

```text
Path smoothing / string pulling
```

This allows actors to walk naturally without being snapped to the center of every tile.

# 27. Important Design Decision

For requirement 20, choose this:

```text
Mutable tilemap + chunked wgpu tile renderer
```

This is the best option for later destructible/buildable dungeon terrain.

The logic crate owns the mutable tile grid.

The renderer owns GPU buffers for chunks.

When walls or floors change, only changed chunks are rebuilt. This keeps the game compatible with future features like digging, building, wall destruction, doors, traps, and terrain effects.
